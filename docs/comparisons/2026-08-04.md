# Mock ↔ real BoondManager — `/times` filtering

> **Superseded on 2026-09-29.** The three shapes tested below are all outside
> the contract. The only filter the RAML documents on `/times` is
> `period=inProgress&startDate&endDate`, on the date of the time row, and it
> works: 111 745 rows unfiltered, 2 716 for September 2026. See
> [2026-09-29.md](2026-09-29.md). The conclusion « no incremental path at all »
> is wrong; the measurements below remain true.

- real: `https://ui.boondmanager.com/api` — production tenant, 106 976 time rows
- mock: in-process `TestClient`
- measured 2026-08-04, from the `insights360` extractor's own client

## The finding

**`/times` accepts the documented period filter and does not apply it.**

| Request | Real API total |
|---|---|
| no filter | 106 976 |
| `startDate=2026-07-01&endDate=2026-07-31` | 106 976 |
| `startMonth=2026-07&endMonth=2026-07` | 106 976 |
| `period=updated&startDate=2026-07-01` | 106 976 |

Three distinct filter shapes, none rejected, none applied. That last part is
what makes this expensive: a `422` would have told the caller something. A
silently ignored filter lets a consumer believe it is fetching a window when it
is fetching everything.

This compounds with an already-registered gap — `times` has no `updateDate`
(see UNVERIFIED-FIELDS, *RAML × observed matrix*). No timestamp to filter on,
and no filter that works. A consumer has no incremental path on this collection
at all, and must size its cadence accordingly.

## What it cost, concretely

`insights360` ran hourly at 100 rows per page. With no incremental filter, that
is a full refresh every hour:

```
106 976 / 100 = 1 070 calls/hour  →  ~25 000 calls/day
```

against a provider that is not ours. Corrected on the consumer side by raising
the page size to the API cap (500) and dropping the cadence to 4 h — 1 284
calls/day for the same useful freshness, since timesheets are filled daily or
weekly.

## What the mock does about it

`CollectionSpec("times", …, filtre_periode=False)`.

The parameters are **accepted and ignored**, exactly as the provider does. Not
turned into a `422`: the real API does not reject them, and a consumer seeing an
error here would fix a problem that does not exist.

Locked by `tests/test_ecarts_api_documentation.py`, which also asserts the gap
stays **local to `/times`** — a `filtre_periode=False` added elsewhere by
mistake would otherwise pass unnoticed and silently cost a consumer its
incrementality.

## Why reproduce a provider defect

A mock has two possible fidelities and they conflict: faithful to the
**documentation**, or faithful to the **observed behaviour**. This repo picks
the second, without exception.

A mock that filters where the provider does not turns its consumer green on
behaviour that does not exist. Sizing, extraction cadence and the load imposed
on the provider are then computed against a fiction — which is precisely what
happened above.

The test will fail the day BoondManager fixes its API. That is the point: the
fix should be **observed**, not assumed.
