# Mock ↔ real BoondManager — behaviours: pagination, sorting, filters

- real: `https://ui.boondmanager.com/api` — production tenant, **9.1.97.2**
- mock: 0.10.0 before this report, **0.11.0** after it, dataset `realiste`, seed 42
- measured 2026-09-29, read-only, **108 GET calls**, with the `insights360`
  extractor's own production credentials
- replayable: `scripts/probe_behaviours.py --target real|mock`
- reference: the official RAML downloaded the same day — `search.raml` and
  `search.json` of 18 modules, trait `sortablePaginable.raml`

## Why this probe happened

The earlier comparisons checked SHAPES: keys, types, envelopes. An audit of the
`insights360` extractor showed that its costliest assumptions were about
BEHAVIOURS nobody had measured: the incremental parameter it sent, the sort it
relied on, the page sizes it asked for. Three findings, all of the same kind —
a parameter accepted with a 200 and ignored — were enough to explain most of an
estimated 15 500 calls per day.

## 1. Pagination

Contract: `maxResults` default 30, maximum 500, on every module carrying the
`sortablePaginable` trait.

| Request | Rows | Reading |
|---|---|---|
| `/actions?maxResults=2` | 2 | honoured |
| `/actions?maxResults=100` | 100 | honoured |
| `/actions?maxResults=101` | 30 | **above the `/actions` maximum: default size** |
| `/actions?maxResults=500` | 30 | same |
| `/companies?maxResults=500` | 500 | honoured |
| `/companies?maxResults=501` | 30 | **above the general maximum: default size** |
| `/agencies`, `/poles`, `/business-units` with `page=2&maxResults=1` | 11, 8, 2 — everything | not paginated, as the contract says |

**Correction.** The 2026-08-12 probe tested `/actions` with 500 only and
concluded « `maxResults` is ignored ». It is capped at 100. And no module caps
at 500: above the maximum, every module falls back to 30 rows, with no error.

## 2. Sorting

Contract: `sort` takes a key from the module's `sortList`, `order=asc|desc`,
default `asc`.

| Request | Result |
|---|---|
| `sort=id`, asc or desc, on resources, companies, actions | same sequence as no sort — `id` is in no `sortList` |
| `/resources?sort=cleInconnue` | 200, default order |
| `/resources?sort=lastName` | honoured, both orders |
| `/resources?sort=creationDate`, asc or desc | **ignored** — the key is in the `sortList` |
| `/resources?sort=updateDate&order=asc` | **descending** — `order` ignored on that key |
| `/companies?sort=updateDate`, `/actions?sort=startDate` | honoured, both orders |

Default order, without `sort`: **`updateDate` descending** on resources and
companies, **`startDate` descending** on actions. Stable between two identical
calls, as observed on 2026-07-31 — but sorted on the most volatile key there
is. A record modified during a paginated scan jumps to the head.

## 4. `/times`

Contract: `period=inProgress&startDate&endDate` — the time rows whose date falls
in the window. No `updateDate`.

| Request | Total |
|---|---|
| no filter | 111 745 |
| `period=inProgress`, 2026-09-01 → 2026-09-29 | 2 716 |
| `period=inProgress`, August 2026 | 2 575 |

**Correction.** The 2026-08-04 report concluded that `/times` had « no
incremental path at all ». The three shapes it tested are all outside the
contract; the contract's own shape works.

## 5. Fields, re-verified

Documented and still never returned (20 rows per module): `/orders`
`creationDate`, `updateDate`, `billableItemTypes`, `requestTimesheetsSignature`;
`creationSource` on the resources, candidates, companies, contacts and
opportunities searches; `numberbOfActiveOpportunity` on companies; `icSince`
and `icStatus` on the resources search.

## What the mock does about it — 0.11.0

| Behaviour | Up to 0.10.0 | Since 0.11.0 |
|---|---|---|
| `/actions` `maxResults` | 30 rows whatever the request | honoured up to 100, 30 above |
| above 500 | capped at 500 | 30 rows |
| agencies, poles, business-units | paginated | everything, `page`/`maxResults` ignored |
| `sort` outside the `sortList` | honoured on any attribute (`id` ignored by accident) | ignored |
| `/resources` `creationDate`, `updateDate&order=asc` | honoured | ignored / descending |
| default order | ascending identifiers | descending dates on resources, companies, actions |
| `updatedSince` | applied | ignored — `BOOND_MOCK_UPDATED_SINCE=true` to apply it |
| `/times?period=inProgress` | ignored | applied on the row date |

Locked by `tests/test_dialecte.py`, `tests/test_ecarts_api_documentation.py`
and `tests/test_ecarts_mesures_en_production.py`.

**Known remaining gap.** `/orders?period=updated` filters on the vendor side
through a date the vendor does not return. The mock has no such hidden date:
on `/orders`, any `period=updated` window returns nothing. A consumer must not
test an incremental `/orders` extraction against the mock.

## Consequences for a consumer

- Build the incremental extraction on `period=updated`, with a one-day overlap:
  it is the only filter the vendor applies.
- Ask 100 rows per page on `/actions`, never more than 500 anywhere: above the
  maximum, the answer shrinks to 30 rows without a word.
- Window `/times` by row date with `period=inProgress`; re-read the whole
  collection periodically, since a correction to an old row has no date to
  find it by.
- Do not rely on `sort=id`. Deduplicate on the identifier within a scan, and
  keep answers small enough to fit in one page whenever possible.
